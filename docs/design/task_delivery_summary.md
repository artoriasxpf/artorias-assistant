# Task 交付总结与跨轮复用方案

## 评估与选择

建议让 LLM 在交付后提炼成果，再由程序把成果合并进 Task。当前实现已保存 Step 全文和交付索引，但 Task 的 `summary` 会被最新 Step 全文覆盖。下一轮只看到有字数上限的旧结果，也可能拿不到关键产物路径、决定和未完成事项。结构化总结能把这些信息从正文里提取出来，帮助后续轮次直接接着做。

总结以**已交付的 Step** 为单位。一次用户输入在当前系统对应一个 Run，Run 可以包含多个 Step 和多个 Task。等整个 Run 结束才总结，容易把不同 Task 的结论混在一起，也会漏掉「第一个 Step 已交付，后续 Step 等待审批、失败或取消」这种情况。每个 Step 的最终回复落库后即可排入总结任务；Run 仍按现有规则汇总回复并结束。

代价是每个需要归纳的 Step 最多多一次正常模型请求，以及短时间内总结尚未生成。首版让总结异步执行，限制输入、输出和并发数。规划或执行下一轮时，尚未完成的总结由对应 Step 的结果引用补足。无需为了等总结而拖延最终回复或重跑工具。

## 数据与职责

| 位置 | 内容 |
| --- | --- |
| `task_steps.result` | 完整最终回复，保留为交付原文。 |
| `task_steps.delivery_seq` | 同一 Task 的交付序号。在交付事务内由 `execution_count + 1` 得到。为历史排序和后台幂等提供依据。 |
| `task_steps.handoff` | 严格校验的 JSON。包含简短成果、决定、未完成事项、已验证的产物引用及证据缺口。 |
| `task_steps.handoff_status` | `pending`、`running`、`ready` 或 `failed`，与 Step 的业务状态独立。重试次数和租约时间也记录在 Step 上。 |
| `tasks.progress` | 保持交付索引，只保留最近 20 条。完整结果或总结需要时按 Run ID 和 Step Key 获取。 |
| `tasks.summary` | 有大小上限的结构化 Task 状态，建议使用现有 TEXT 列保存 JSON，由查询或界面渲染。存当前进展、仍有效的决定、关键产物引用和待办，以及处理到哪个交付序号。 |

每次交付不重新复制历史正文。建议首版每个 `handoff` 限制为 2 KB，Task 的 `summary` 限制为 4 KB，均按序列化后的 UTF-8 字节计。未完成事项和关键产物优先保留，较旧内容可通过 Step 引用回查。估算上，100 个 Step 的归纳正文上限约 200 KB，另有数据库索引和存储开销。

Task 的 `revision` 继续表示**长期需求版本**。交付总结不会改变 `goal`、`constraints`、`criterias` 或递增 `revision`。Step 的 `applied_revision` 仍说明当时执行的是哪个需求版本。旧版本的交付可以进入历史，但不能自动标记当前版本的验收标准已满足。

## 写入、归纳、合并

1. 在 `TaskRepository.deliver()` 的现有事务中保存最终回复、交付序号、进度索引及待归纳状态。保留已有的幂等判断。同一个 Run 和 Step Key 重试不会重复累计交付次数或重复入队。
2. 在应用启动时启动独立的总结 Worker。它用短事务领取待归纳 Step，先提交领取状态，再调用 LLM。同一 Task 按交付顺序处理，首版全局并发设为 1。进程中断后，过期的总结租约可重新领取，因为该调用不带工具，也不会重复执行用户操作。
3. 一次 LLM 请求产出 `handoff` 和 Task 状态变更。输入仅包含本次目标、有效需求版本、最终回复、已有 Task 状态和已确认的执行证据。校验严格 JSON 结构、字节预算和引用。失败可纠正重试一次，仍失败则记录 `failed`，业务交付结果保持可读。
4. 用程序合并有证据的增量。按稳定 ID 或引用去重，只有本次有相应证据时才关闭待办或替换产物。产物由程序核对文件变更或 Python 发布记录，保留工作空间、路径、版本及 Change ID；模型不得自行认定某个文件已成功生成。未建立完整扫描清单时，归纳只能记录覆盖未知，不能报精确未读数量。
5. 在一个事务中写入 `handoff` 与新的 Task 状态。提交前比对 Task 的需求版本和尚未更新的总结游标。过期结果可以保存为该 Step 的历史归纳，但不能覆盖更晚的 Task 状态或在新需求版本下宣称完成。总结失败的 Step 保留缺口和全文引用，后续 Step 可以继续归纳。

建议在 `tasks/delivery_summary.py` 实现 Schema、模型调用和合并，在 Task 仓储里实现领取及提交接口。Worker 由应用 lifespan 管理，交付入口仍在 `TaskRuntime.execute()` 和 `TaskRepository.deliver()`。首版复用 Step 表作为待归纳任务来源，避免增加独立队列表。

## 下一轮怎么使用

`ContextBuilder` 优先传入 Task 的当前状态和最近 5 个有归纳的 Step，附完整结果引用。待归纳或归纳失败的 Step 仍提供状态和 `task_result_read` 引用；现有的原文预算内预览也可作为兜底。规划器接收精简的 Task 状态。如果后续属于同一任务链，推荐规划为继续同一个 Task；如果必须新建后续 Task，另行提供受同一 Session 限制的来源成果引用。无需共享 Agent 执行线程。

例如，第一轮扫描目录后，Task 状态记录「报告已生成」及其已验证路径，并注明覆盖范围。第二轮优先从报告生成建议，第三轮复用建议并只核对要操作的文件和目标冲突。旧授权仍按当前 Run 的权限规则处理。

## 验收

- 单个 Run 有两个 Task 时，分别保存两个 Step 的归纳；后续 Step 等待审批或失败不影响已交付的 Step。
- 总结超时、输出无效、服务重启时，用户仍能拿到原始交付；重复领取不会把相同成果合并两次。
- 验证假产物路径和没有扫描证据的未读数量不能被记录成事实。
- 永久需求修改才递增 `revision`；旧归纳迟到时不能覆盖较新的 Task 状态。
- 用「扫描 → 建议 → 整理」回归测试，检查后两轮能复用前轮产物，并比较再次读取原文件的次数。
